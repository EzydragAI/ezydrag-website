The harness, in 100 seconds

An agent is a model plus a harness. Addy Osmani wrote it up for O'Reilly with Viv Trivedy's line: "Agent = Model + Harness. If you're not the model, you're the harness."

Lilian Weng calls a harness "the system surrounding a base model that orchestrates execution." Context. Tools. Memory. Checks. Logs. Everything that isn't the model.

Your model is fine. Your model has always been fine.

Why it decides everything

Osmani again: "A decent model with a great harness beats a great model with a bad harness."

When an agent misbehaves, people blame the model. Usually it's missing context, a tool with far too much access, or no check before the action. A skill issue. On the build side.

60%

of harnesses big enough to assess had neither a test nor an eval, in Marmelab's September study of 246 repositories.

It gets worse

Same study: only 4.4% of security rules in public CLAUDE.md files were backed by a real control. The rest were vibes, written in Markdown.

What to do

  • Don't shop for models first. Shop for a team that can build and run the harness.
  • Every mistake becomes a rule. Each line in a good instruction file should trace back to something that went wrong.
  • Keep the rulebook short. Osmani's phrase: a "pilot's checklist, not style guide."
  • Keep state in files. Weng's advice for long-running agents: "keep durable state in files."

How we do it at Ezydrag

Most of our build time goes into the harness, not the prompt. Context from your CRM and marketing data, tools with narrow access, approvals, logs, tests. When a better model ships, we swap it in. The harness stays. This has been the harness, in 100 seconds.
